# Tactus 產品定位與設計原則

Tactus 是通用、Python-first 的 Agent 音樂製作 runtime，讓 Agent 用熟悉的程式語言製作、試聽與修改音樂。Tactus 盡量把 creative decisions 留給 Agent 本身，負責讓製作過程可靠執行，並交付可比較、可追溯的結果。

本文件獨立定義產品定位、責任邊界與設計原則，供實作與 review 使用，隨決策更新。它描述產品應滿足的方向，不代表所有能力已經交付。

## 1. 創作決定盡量留給 Agent

Agent 選擇素材、音符、處理順序、routing、automation、分軌與混音比例，並使用自己的聽覺工具、分析結果與人類回饋判斷作品。

設計 API、預設值與便利功能時，要檢查它們是否替 Agent 做了創作決定。盡量讓 Agent 明確選擇或自行表達；必要的預設應清楚可見、可以覆寫。技術上的便利不應默默決定作品的節奏、音色、結構或美學。

Tactus 負責製作過程中反覆需要正確的工作：音訊與工具間的銜接、時間處理、素材管理、試聽、驗證與結果追溯。音樂手法可以作為可選的創作語彙，但不能成為限制作品形式的強制流程。

作品的品質問題（例如音量過大）由 Tactus 如實回報，讓 Agent 自己察覺並處理；Tactus 不替 Agent 擋下，因為擋下只會讓 Agent 想辦法繞過去，問題依然存在（2026-09-25，由滿格檢查改為音量回報）。

給 Agent 的 `tactus` plugin 以 `compose`、`dsp`、`measure`、`version` 四個 skills 提供可組合的創作能力：用 functional、modular 的 Python 維護作品，使用或撰寫 DSP 與分析，再把觀察轉成自己的音樂決定，並用 Git 保存修訂。程式的入口、模組契約與實作依 progressive disclosure 組織，讓修訂能逐步找到相關邏輯。範例與內建 source 是可改寫的參考，不規定曲式、風格、固定資料夾或創作順序；套件自己的 API 仍由其文件負責（2026-09-30）。

## 2. 創作意圖只有一份權威來源

Code as source of truth：Python source、版本化的素材身分與 dependency lock 共同承載創作決策，Git 記錄修訂。素材檔案可以放在 Git 外，但作品必須明確指向所使用的內容；替換素材也是應被版本記錄的創作變更。

生成的編排、音訊、執行紀錄與 cache 都是衍生結果。選定的演奏若要跨修訂保留，
就保存成作品明確引用的素材（take）；採用哪個內容身分是 source 裡的創作決定。若 runtime 需要 graph，它也由 source 產生。作品應只有一套需要維護的創作依據，避免要求作者同步修改 code 與另一份作品模型。

## 3. 順應 Agent 自然的工作方式

Agent 可以直接用 Python、NumPy 與既有套件表達合成、取樣、MIDI、DSP、編曲與特殊做法。Tactus 接納這些創作方式，讓它們能使用共同的執行能力。

普通 Python、函式與 NumPy 都是正式創作途徑。Agent 能否理解、完成並修改作品，是設計是否合適的判準。Agent 自己寫 NumPy 是正常創作，不能單憑這件事判定它繞過了 Tactus。

Tactus 提供自己維護的 analysis 與 DSP：掌握演算法、數值定義、介面與測試，讓常用能力可以持續改善。核心依賴盡量少，優先以 NumPy／SciPy 實作，有量測依據時再採用 Numba 等加速工具。自有實作仍須驗證正確性與維護成本，但不要求每項都比第三方更快；pyqmdsp、pytimestretch 等高成本專門能力保留依賴。內建功能是可選工具，作品仍可自行寫 code、使用其他套件或 VST（2026-09-29）。

## 4. 只要求作品真正需要的共同假設

抽象應保留不同創作形式的表達空間。作品不必先轉成 Track、Bus、Session、Project 或全域 Pattern 模型；這些概念可以在有幫助時使用，不預設所有作品都有固定軌道結構或同一種編曲方式。

作品可以有全曲 tempo、局部節奏、絕對時間，或混合使用。全曲 BPM 是選項；自由時間的作品也應能自然表達。

時間工具協助作者表達與處理關係。變更一種時間設定，只應影響依賴它的內容；不應迫使所有作品接受同一種節拍網格或時間模型。

## 5. 每個功能都需要存在的理由與驗證

每當新增功能，都要有足夠的證據回答「為什麼這個功能要存在？」：它服務哪個真實需求、解決什麼問題，以及相較於現有做法帶來什麼價值。這項要求適用於所有功能，包括 API、CLI、helper 與執行機制。其他產品有這個功能，或設計看起來比較完整，都不足以單獨構成理由。

存在理由必須經過驗證。可以在實作前透過既有使用紀錄、問題重現或小型實驗取得證據，也可以先以明確假設實作，再透過實際使用、比較或聆聽驗證。選擇事後驗證時，要保留尚待驗證的問題與判斷標準；功能完成本身不代表它的價值已被證明。

驗證方式與投入應符合主張的範圍。可以驗證新能力是否滿足需求、是否減少錯誤或製作負擔，也可以驗證創作與修訂是否更容易完成。若結果不支持原先理由，就重新考慮縮小、修改或移除功能，不因已經實作而繼續保留。

對共用 abstraction 而言，先讓作品用普通 Python 函式清楚表達輸入、輸出與處理順序。一次性的音樂邏輯與例外留在作品中；不同任務反覆遇到同一種執行問題，才有理由將它提升為共用能力。省下幾行程式不足以單獨證明 core API 必要，共用能力也必須保留作者的創作選擇。

## 6. 探索應可捨棄，接受才形成修訂

Agent 應能產生候選、聆聽或量測、比較，再決定是否接受。候選彼此隔離，捨棄試聽不改變正式作品；接受候選才成為可追溯的創作修訂。

試聽必須忠實反映候選在作品中的聲音，讓比較有意義。執行方式與效能優化應服務這個循環，而不能讓候選污染正式作品或讓結果失去可比較性。

## 7. 承諾必須符合證據

Tactus 驗證明確宣告的技術要求，不把未要求的混音偏好當作正確性。分析得到的 tempo、onset、pitch 或 loudness 是提供給作者的觀察，不會自動成為創作意圖。

技術檢查通過不代表音樂成立，實際製作、修訂與聆聽仍是產品驗收的一部分。能力與可重現性的承諾必須符合已驗證的範圍；能重播已保存的結果，不等於重新執行任意 source 都能產生相同聲音。

## 如何運用這些原則

即使換掉套件、API 或 runtime 實作，這些要求仍然成立。比較設計方案時，用它們判斷哪個方案更能保留創作自由、維持作品的一致性，並降低真實製作負擔。
