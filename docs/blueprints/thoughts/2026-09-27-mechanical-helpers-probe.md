## 結論

**helper 有幫助，依事先規則可以整合。**兩組都是零錯誤，但有 helper 的組兩輪平均少用 21% token，
程式碼短約三分之一。另外它們在「音量達標又不超過上限」這件事上做法一致，沒有 helper 的組則各自發明了三種做法，
其中兩個用 `np.clip` 硬削了兩萬多個樣本。

| | 錯誤（兩輪） | tokens（兩輪累計） | song.py 行數 |
|---|---|---|---|
| H1 / H2 / H3（有 helper） | 0 / 0 / 0 | 118k / 107k / 101k，平均 109k | 163 / 149 / 124 |
| N1 / N2 / N3（沒 helper） | 0 / 0 / 0 | 126k / 142k / 145k，平均 138k | 210 / 213 / 229 |

第一輪 H 組 3.5–5.5 分鐘，N 組 6–8.5 分鐘；第二輪（改需求）兩組都在 1–2.5 分鐘內完成。

## 題目

48 kHz、8 小節 4/4，含依拍位置線性的漸快。要交的輸出：
- 鼓的音軌：kick、snare、hat 三軌和 `drums` 總和；
- marker 軌：barlines、kicks、quantized、echo。

刻意放進上次各 Agent 寫法分歧的地方：
- 44.1k 立體聲、48k 單聲道且起音前有 30 ms 靜音、96k PCM24 的 sample，每一擊的起音都要切齊；
- 第一擊大鼓提早，頭被切掉；
- quantize 有好幾個剛好在兩格中間的點；
- delay 依音符值與當下 BPM 換算；
- `drums` 的 RMS 要在交付的檔案上量到，peak 不超過 −1 dBFS。

第二輪同時改六項：tempo、換成 22.05k 的 shaker、提早量、quantize 強度、音量目標、delay 音符值。

評分用 `check.py` 對照 `truth.py` 的獨立公式。評分程式先用兩份獨立寫的正確解驗證過，兩份的輸出逐位元相同；
七種故意做錯的版本也都被對應項目抓到：
- 平手用偶數優先；
- 頭用 `np.roll` 繞回尾端；
- 沒切掉起音前的靜音；
- 沒轉取樣率；
- 在 limiter 之前量音量；
- 重疊的 marker 相加；
- delay 用第 1 小節的 BPM。

| helper | H 組使用 | 判定 |
|---|---|---|

## 需要誠實記下的地方

- **評分程式修正了一次，發生在看到任何 H/N 差異之前。**N3 第一輪用 `librosa.resample` 轉 96k 的 hat，
  與真值（`resample_poly`）的相關係數只有 0.946，被判錯。查證後，兩者對齊位置完全一樣，差異只在濾波器處理 Nyquist 附近高頻的方式不同，
  所以轉檔沒有錯。門檻從 0.98 降到 0.90 後，七個故意做錯的版本仍然全部被抓到。
- **N3 第二輪的 `hat_resample` 也不算錯。**librosa 的預振鈴讓「第一個達到 1% peak 的樣本」早了 44 個樣本（0.9 ms），
  而 N3 是照規則對自己轉好的音檔去切的。對齊後相關係數 0.979，起音位置也在 1 ms 容許範圍內。
  這表示題目的「起音」定義會隨轉檔器差不到 1 ms，是規格本身的限度。
- **第 8 小節的 fill 沒寫清楚**要不要跟原本第 0、2.5 拍的大鼓疊在一起。真值是「取代」，所以「重疊 marker 只算一個點」這項，
  只有在 Agent 自己產生重複拍點時才會被測到；六個 Agent 都沒有，所以 `markers` 的這條規則沒有被真正考到。
- **`fit_rms` 也會削平波峰。**它靠 Pedalboard `Limiter`，而那個 limiter 本身會硬削。H 組交付的檔案有 675（第一輪）與
  2641（第二輪）個樣本平貼在 −1.4／−1.32 dBFS。N1、N2 用 `np.clip`，平貼的樣本是 7559 與 22332 個。
  N3 自己先加重壓縮器再 limit，平貼的最少，只有 51 與 190 個。所以整合時 `fit_rms` 不能直接沿用原型：
  要嘛換成不會平頂的做法，要嘛在文件裡寫明它會平頂、會平頂多少。
