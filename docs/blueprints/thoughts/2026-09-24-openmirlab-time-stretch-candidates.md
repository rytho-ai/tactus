# OpenMIRLab time-stretch candidate survey

> 2026-09-24 · Primary-source survey for a possible Python/NumPy-facing OpenMIRLab package. This identifies candidate *roles*, not a decision to bundle or maintain every engine. It complements the [earlier engine survey](2026-09-23-time-stretch-competitors-research.md) and [listening probe](2026-09-24-time-stretch-algorithm-listening-probe.md).

## Separate the layers

An **engine** supplies an algorithm; a **wrapper** gets audio to it. `pyrubberband` is an ISC-licensed file/CLI wrapper, not a distinct algorithm. It writes files, calls the Rubber Band executable, and reads results. Rubber Band is the GPL-2.0-or-later/commercial-licensed engine, with R2/R3 and an offline key-frame mapping API. `rubband` is another, in-memory binding to that same engine. Replacing `pyrubberband` with `rubband` would change integration cost and API exposure, **not** add a second sonic choice. [pyrubberband README](https://github.com/bmcfee/pyrubberband#readme), [Rubber Band README](https://github.com/breakfastquay/rubberband#readme), [Rubber Band API](https://www.breakfastquay.com/rubberband/code-doc/), [rubband README](https://github.com/rec/rubband#readme).

The working Tactus baseline remains Rubber Band. The listening result does not establish a universal quality winner or settle R2 against R3: A/B/C were randomized separately per source/ratio, and the preferred cell was not identified. [Listening probe](2026-09-24-time-stretch-algorithm-listening-probe.md).

## Candidate roles

| Candidate | What it actually adds | Python / integration and license | Present disposition to investigate |
| --- | --- | --- | --- |
| [Signalsmith Stretch](https://github.com/Signalsmith-Audio/signalsmith-stretch#readme) | A genuinely different C++ pitch/time engine. Upstream says its time stretching is best for moderate changes, roughly 0.75×–1.5×; it exposes streaming block processing, latency queries, and seek/flush. | MIT. The independently maintained [python-stretch](https://github.com/gregogiudici/python-stretch#readme) binding is also MIT, takes NumPy arrays, and publishes platform wheels. | Strongest **low-integration-cost second-engine probe** for modest music/speech adjustments. In the current small blind test it was not shown to beat Rubber Band generally. Its wrapper is not the engine's upstream project; evaluate both separately. |
| [Bungee](https://github.com/bungee-audio-stretch/bungee/blob/main/README.md) | Its granular C++ API lets the caller set source position, speed, and pitch per grain, including reverse, zero speed, seek, and scrub. Its simpler streaming API is forward-only. This addresses a different capability question: nonlinear source-position control. | MPL-2.0. Upstream supplies C++ headers/library, releases and CLI; no upstream Python binding is documented in its README. A binding/integration layer and channel/buffer tests would be our responsibility. | Strongest **capability-led candidate** if Tactus needs continuously varying or non-monotonic warp that the existing marker workflow cannot express satisfactorily. Not a low-effort generic replacement. |
| [SoundTouch](https://soundtouch.surina.net/README.html) | C++ engine and SoundStretch CLI for independent tempo, pitch, and playback-rate controls; conventional time-domain processing. | LGPL according to its official README. The CLI accepts WAV files or WAV streams through `stdin`/`stdout`; upstream's documented package does not make an in-memory NumPy API available by itself. | Useful lightweight conventional baseline or compatibility target. Do not add solely for having another name; first find a material/workflow where it provides a measurable benefit. |
| [PyTSMod](https://github.com/KAIST-MACLab/PyTSMod#readme) | Python implementations of OLA, WSOLA, TD-PSOLA, phase vocoder, and related methods. Its README documents Python/NumPy/SciPy/SoundFile inputs and a CLI; TD-PSOLA additionally needs pitch data, and the CLI does not support nonlinear TSM. | GPL-3.0. Its public GitHub organization reports the repository last updated in 2023; check current support and Python-version compatibility before making it a dependency. | Valuable **algorithm reference and comparison fixture**, especially for contrasting WSOLA and phase-vocoder behavior. Multiple algorithms inside one package are not automatically multiple mature production backends. |
| [AudioTSM](https://github.com/Muges/audiotsm#readme) | Python OLA/WSOLA/phase-vocoder implementations with a block/stream processing interface. | MIT. Its README still advertises Python 2.7/3.4+; modern Python packaging and NumPy behavior need a fresh compatibility check. | Another useful readable reference or simple fallback; not yet an evidenced reason to replace Rubber Band. |
| [librosa.effects.time_stretch](https://librosa.org/doc/dev/_modules/librosa/effects.html) | Already in Tactus's analysis dependency family; supplies fixed-rate phase-vocoder stretching on arrays. | Python/NumPy API; librosa is [ISC-licensed](https://github.com/librosa/librosa/blob/main/LICENSE.md). This is an existing dependency path, not a new native engine to maintain. | Useful zero-new-backend baseline, tests, and creative phase-vocoder option. Do not infer parity with Rubber Band for transient-rich production audio. |
| [PaulXStretch](https://github.com/essej/paulxstretch#readme) / [PaulStretch](https://hypermammut.sourceforge.net/paulstretch/) | Deliberate *extreme* stretch and spectral smearing for ambient/sound design. The maintainer explicitly says PaulXStretch is unsuitable for subtle corrections. | PaulXStretch is GPL-3.0 with an App Store exception and is primarily a standalone/plugin application, built with JUCE and FFTW; the original PaulStretch is GPL-2.0. Neither is a ready-made NumPy binding. | Potential **special-purpose creative effect**, not a general-purpose second adapter or substitute for sample-aligned warping. Integration/license work is nontrivial. |
| [FFmpeg `atempo`](https://github.com/FFmpeg/FFmpeg/blob/master/libavfilter/af_atempo.c) / [`rubberband`](https://github.com/FFmpeg/FFmpeg/blob/master/libavfilter/af_rubberband.c) | `atempo` is a separate FFmpeg filter implementation; `rubberband` calls librubberband and is therefore the same engine as the baseline. | FFmpeg filter subprocess integration adds a separate binary/build dependency; the `rubberband` filter depends on librubberband being present in that FFmpeg build. FFmpeg's filter source alone does not confer a different license on Rubber Band. | Good interoperability/CLI comparison, not an independent candidate in the `rubberband` case. Test `atempo` only if an FFmpeg-oriented workflow supplies a real use case. |

There is also a [recent Python `paulstretch` package](https://pypi.org/project/paulstretch/) claiming a modern implementation, but this survey has not audited its source, license provenance, or audio behavior. It is a lead for an *extreme-stretch* probe, not a validated integration recommendation.

## What would justify adding one?

The next backend should fill a demonstrated hole in one of two directions:

1. **Ordinary moderate stretch with genuinely better results or deployment properties:** compare Signalsmith against Rubber Band on named source/ratio cells, explicit R2/R3 settings, matched output length/alignment, and user listening. Its permissive native engine plus published NumPy binding make it cheap to investigate, but no source establishes a quality win in advance.
2. **A capability Rubber Band's current Tactus path does not adequately expose:** test Bungee with a changing, pausing, and reversing source-position curve. This is a different creative control, not just another `stretch(audio, ratio)` implementation. Measure boundary clicks, marker correspondence, latency, and integration effort as well as sound.

PyTSMod, AudioTSM, librosa, SoundTouch, FFmpeg, and PaulStretch-family software are useful baselines or specialist tools; their inclusion in one distributable package should follow a specific production need. Upstream license labels here are discovery facts, **not** a conclusion that bundling or linking the engines into one OpenMIRLab distribution is legally compatible. Recheck the exact distribution topology and licenses before packaging.
