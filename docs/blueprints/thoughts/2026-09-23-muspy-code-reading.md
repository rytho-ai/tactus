# MusPy code reading: MIDI authoring mechanisms

> 2026-09-23 · Source reading, not an Agent usability experiment or a Tactus API decision. This note concerns MusPy's documented `latest` source; behavior should be checked against a pinned installed version before depending on it.

## Question

Which implementation ideas in MusPy are relevant to Python/NumPy-first MIDI authoring, even if MusPy itself is not selected as the MIDI editing layer?

## Mechanisms worth examining

1. **Note-level intermediate representation.** `Music` holds global `resolution`, tempo and meter changes, and tracks; `Track` holds notes, chords, lyrics and annotations. `Note` stores absolute metrical `time`, `duration`, pitch and velocity, with `start`/`end` accessors. This is a readable in-memory result of executing Python code, separate from the lower-level note-on/off MIDI messages. [Music source](https://muspy.readthedocs.io/en/latest/_modules/muspy/music.html) · [Note and Track source](https://muspy.readthedocs.io/en/latest/_modules/muspy/classes.html)
2. **Time transforms operate on both ends of a note.** `Base.adjust_time` recursively applies a supplied function to timed objects. `Note.adjust_time` computes a new onset and a new duration from the transformed *old end*, rather than shifting the onset while leaving a stale duration. This is a concrete pattern for tempo-grid or phrase edits; the creative transform remains an ordinary Python function. The mutation is in-place, and the source does not make the function monotonic or the resulting duration valid automatically. [Base source](https://muspy.readthedocs.io/en/latest/_modules/muspy/base.html) · [Note source](https://muspy.readthedocs.io/en/latest/_modules/muspy/classes.html)
3. **Musical coordinates are explicit.** MusPy stores integer time steps and a `resolution` in steps per quarter note; MIDI import carries over the file's PPQ. Tempo lives in separate timed `Tempo` objects. Thus a note's metrical position need not be recalculated when only tempo changes; conversion to absolute playback time is a different operation. [Timing documentation](https://muspy.readthedocs.io/en/latest/timing.html) · [MIDI import source](https://muspy.readthedocs.io/en/latest/_modules/muspy/inputs/midi.html)
4. **Small structural contracts and generic tree operations.** Classes declare `_attributes`, optional fields and list fields. `Base.from_dict`/`to_ordered_dict` use these declarations for conversion; `validate` can recursively check types and values. `ComplexBase` adds type-directed append, sort, duplicate removal and invalid-item removal. The separation of a small data model from mechanical tree operations is reusable as an idea. Validation is explicitly called, not enforced on every mutation; `from_dict` defaults to `strict=False`. [Base/ComplexBase source](https://muspy.readthedocs.io/en/latest/_modules/muspy/base.html) · [Class declarations](https://muspy.readthedocs.io/en/latest/_modules/muspy/classes.html)
5. **One semantic object, several task-specific projections.** MusPy converts `Music` into note arrays, piano rolls, event sequences and pitch sequences. The note-based projection is `(time, pitch, duration, velocity)`; the event-based projection is token-like note-on/off/time-shift/velocity data. These representations answer different computation needs, rather than all being editable sources. [Representation documentation](https://muspy.readthedocs.io/en/latest/representations/index.html)
6. **MIDI import exposes an ambiguity policy.** For repeated note-on messages at the same pitch and channel, `from_mido` documents FIFO, LIFO and `all` note-off matching policies. It also treats a zero-velocity note-on as a note-off. This shows that importing MIDI into note objects is not merely parsing bytes: some source performances require a declared interpretation policy. There is also a concrete code discrepancy: the argument validator accepts `all`, while the branch that closes every active note checks `close_all`. The documented `all` behavior needs a runtime regression test before use. [MIDI import source](https://muspy.readthedocs.io/en/latest/_modules/muspy/inputs/midi.html)

## Fidelity and source-of-truth limits visible in code

- **Annotations are not a general MIDI passthrough.** `from_mido` converts control changes into `Track.annotations`, but `to_mido_track` emits only track name, program change, and notes. The input code has no pitchwheel branch. Consequently the default Mido path cannot be assumed to preserve sustain CC64 or pitch bend through a `MIDI → Music → MIDI` cycle. [Input source](https://muspy.readthedocs.io/en/latest/_modules/muspy/inputs/midi.html) · [Output source](https://muspy.readthedocs.io/en/latest/_modules/muspy/outputs/midi.html)
- **Track identity is not identical to MIDI channel identity.** Import groups active material by MIDI track, `(program, channel)`; export assigns channels from track order, skipping the drum channel and cycling after 15 non-drum tracks. That can change channel assignments on round-trip and deserves semantic, not byte-for-byte, checking. [Input source](https://muspy.readthedocs.io/en/latest/_modules/muspy/inputs/midi.html) · [Output source](https://muspy.readthedocs.io/en/latest/_modules/muspy/outputs/midi.html)
- **Same-tick event order needs its own policy.** The exporter collects absolute-time Mido messages, then sorts by time alone before producing delta times. That does not itself encode a priority for simultaneous note-off, note-on, CC, or tempo events. Where ordering matters, a consumer needs a stable tie-break and a regression test. [Output source](https://muspy.readthedocs.io/en/latest/_modules/muspy/outputs/midi.html)
- **A MusPy object need not become a second editable artifact.** `Music.from_dict` and JSON/YAML I/O make serialization possible, but Python source could instead construct the object each run and emit MIDI as a derived artifact. This is an architectural inference from the available constructors and I/O, not a requirement imposed by MusPy. [Music source](https://muspy.readthedocs.io/en/latest/_modules/muspy/music.html) · [Base source](https://muspy.readthedocs.io/en/latest/_modules/muspy/base.html)

## Evidence boundary

The code reading identifies mechanisms and round-trip risks. It does **not** show that adopting MusPy, copying its class hierarchy, or making tracks mandatory would improve Agent first-pass correctness over Symusic or task-local Python events plus Mido. That requires a controlled editing task with the same source, agent conditions, and semantic MIDI checks.
