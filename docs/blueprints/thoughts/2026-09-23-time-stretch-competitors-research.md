# Time-stretch engine alternatives to Rubber Band

> 2026-09-23 · Primary-source research for Tactus's offline, Python/NumPy-first music workflow. This is a shortlist, not a listening-test result or a backend decision.

## Start with the right comparison

`pyrubberband` is not a time-stretch algorithm. It writes temporary audio files and invokes the Rubber Band command-line program; its `time_stretch` and `timemap_stretch` functions are interfaces to the same underlying engine. Unless an R3 option is passed through `rbargs`, invoking the `rubberband` command selects the default R2 engine; comparisons should record which engine was selected. [PyRubberband implementation](https://github.com/bmcfee/pyrubberband/blob/main/pyrubberband/pyrb.py), [Rubber Band README](https://github.com/breakfastquay/rubberband#2-using-the-rubber-band-command-line-tool).

The newer [`rubband` binding](https://github.com/rec/rubband) is also **the same Rubber Band engine**, not a sonic competitor. It exposes NumPy-compatible, in-memory `stretch(...)` and stateful `Stretcher` APIs through a native binding. Its documented limits include contiguous CPU `float32` input, Rubber Band 4.x for source builds, and GPL-2.0-or-later terms for the binding; it is not a hard-real-time Python guarantee. This makes it a potentially relevant *integration* alternative to `pyrubberband`'s temp-file/subprocess path. Its actual wheel availability, API coverage needed by Tactus (especially key-frame maps), and behavior on our target platforms still need verification. [README and examples](https://github.com/rec/rubband#minimal-examples), [known limitations](https://github.com/rec/rubband#known-limitations). Rubber Band itself offers R2/R3 engines, offline two-pass processing, and an offline source-to-output sample key-frame map; its upstream license is GPL-2.0-or-later or commercial. [API](https://www.breakfastquay.com/rubberband/code-doc/), [license](https://github.com/breakfastquay/rubberband#licence).

## Different engines worth knowing about

| Engine | Evidence-backed fit | Integration and constraint |
| --- | --- | --- |
| [Signalsmith Stretch](https://github.com/Signalsmith-Audio/signalsmith-stretch) | MIT C++ pitch/time library. Its README explicitly says time-stretch sounds best for **modest** changes, about 0.75–1.5×; varying input/output block sizes sets the time ratio. It therefore deserves a test for ordinary adjustments, not an assumed win for extreme warps. | [`python-stretch`](https://github.com/gregogiudici/python-stretch) already exposes NumPy arrays and a `timeFactor` in Python. This appears to be the lowest-friction genuinely different engine to compare with Rubber Band, but is an integration inference, not a benchmark. The binding is third-party; confirm wheels, channel layout, and behavior in Tactus rather than treating upstream C++ support as Python support. |
| [Bungee (open source)](https://github.com/bungee-audio-stretch/bungee) | MPL-2.0 C++ library for real-time or offline stretch/pitch processing. Its granular API lets the caller set source position, speed, and pitch per grain, including zero and negative speeds; the simpler streaming API is forward-only. This is especially relevant if Tactus needs nonlinear warp, scrub, or reverse-play semantics. | Upstream ships C++ API, shared-library releases, and a CLI. A [third-party Python binding](https://pypi.org/project/bungee-python/) exists, but its coverage and reliability are unverified here. The expressive granular path is more integration work than calling a file-level `stretch` function. Bungee Pro is a separate [commercial offering](https://bungee.parabolaresearch.com/). |
| [SoundTouch](https://soundtouch.surina.net/README.html) | LGPL C++ library/`SoundStretch` CLI for independent tempo, pitch, and playback-rate changes; upstream documents a music-oriented default and a speech switch. A credible lightweight baseline for conventional tempo changes. | File-level use is straightforward through its CLI; in-memory Python use would need a binding or native integration. Its upstream API description does not establish parity with Rubber Band's sample-anchored offline key-frame map. [README](https://soundtouch.surina.net/README.html). |
| [zplane élastique Pro SDK](https://licensing.zplane.de/uploads/SDK/ELASTIQUE-PRO/V3/manual/elastique_pro_v3_sdk_documentation.pdf) | Proprietary/commercial SDK with time-stretch and pitch-shift modes. Its documented `CElastiqueWarpAPI` supports input/output synchronization points, making it a direct feature-level candidate for marker-driven warp. The API also supports blockwise factor changes. | Requires a commercial SDK/license and a C++ integration/binding; the public SDK documentation is evidence for capability, **not** for comparative sound quality or Tactus-ready packaging. Pricing/redistribution terms must be confirmed with zplane before adoption. |
| [Superpowered TimeStretching](https://docs.superpowered.com/reference/latest/time-stretching/) | Proprietary SDK with native/WebAssembly real-time processing and an official offline example. It exposes tempo, pitch, formant correction, and sound presets aimed at complete music versus isolated instruments. | Its pull-style C++/WebAssembly API and licensing are a larger fit gap for Tactus's current offline Python boundary. It is relevant if browser/live playback becomes a requirement, not an obvious first replacement for the current offline path. [API](https://docs.superpowered.com/reference/latest/time-stretching/), [SDK licensing information](https://superpowered.com/web-assembly-audio-javascript-web-audio). |
| [SBSMS / libsbsms](https://github.com/claytonotey/libsbsms) | GPL-2.0 subband sinusoidal-modeling engine with an example CLI for sliding time stretch and pitch shift. This is a distinct algorithm family, not merely a wrapper around Rubber Band. | Upstream says the current branch is mostly maintained for Audacity and descendants, and that callers must set their own output stopping condition because the library zero-pads indefinitely. Treat it as a specialist reference, not a default candidate without a concrete advantage. [Maintainer README](https://github.com/claytonotey/libsbsms/blob/main/README.md), [source license](https://github.com/claytonotey/libsbsms/blob/main/LICENSE.txt). |

## Implication for the next Tactus decision

Keep Rubber Band as the known-good baseline. If the question is **Python/NumPy integration overhead**, test `rubband` against `pyrubberband` first: this changes the wrapper, not the algorithm. If the question is a **different sonic engine with low Python friction**, Signalsmith Stretch via `python-stretch` is the clearest next candidate. If the question is **nonlinear, continuously controlled source position**, Bungee and élastique's warp API are stronger capability probes. SoundTouch is a useful simple baseline; Superpowered and SBSMS are secondary unless their specific strengths become required.

No primary source establishes a material-independent sound-quality ranking against Rubber Band. That requires matched source files, ratios, engine settings, output alignment, and listening. License compatibility also needs review for the chosen distribution model; this note records upstream terms, not legal advice.
