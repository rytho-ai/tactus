# 時間工具（A1）必要性 probe：沒有證明需要

> 2026-09-26～27 · 依[計畫](../plans/2026-09-26-temporal-abstraction.md)第 1 步。判定規則在試驗前寫定
> （scratchpad `probe-time/PREREGISTERED.md`）。起點是先重讀之前的時間相關 probe：
> - [混合時鐘 probe](2026-09-23-mixed-clocks-vs-python-probe.md)建議下一步測「在真實修改上」比較兩種做法，
>   所以這次以修改輪為主要判定；
> - 當時發現的「必須寫假 BPM」缺陷，已由 `render()` 的設計消除。

## 結論

**沒有證明需要。**沒有工具的組兩輪都全對，token 只多 9%，未達 1.3 倍的門檻。A1 維持在 Future，
等實際作品出現時間計算錯誤再重新考慮。

這和之前的 probe 一致：Agent 用普通 Python 就能把時間算對，第一次寫與修改時都一樣。

## 設計

- **原型：**`tclock.py`，放在 scratch，沒有進產品。功能包括：
  - tempo map，支援線性漸變；
  - 拍號變化；
  - 起始秒數；
  - 一律直接計算、只取整一次；
  - `place` 與兩種 envelope（依拍位置線性、依時間線性）。
- **正確答案：**由 `truth.py` 用公式計算，不依賴原型；我和原型交叉比對過，逐樣本一致。
  評分由 `score.py` 讀取 render 出來的音檔，比對每個 impulse 的 frame、長度與曲線。
- **題目**（48 kHz，取整規則寫在題目裡）：
  1. `ramp.py`：16 小節，第 9～13 小節依拍位置從 90 BPM 線性漸快到 110 BPM；kick、clap，以及跟著拍位置走的 sweep；
  2. `meter.py`：前 4 小節 7/8、後 4 小節 4/4，十六分音符 60% swing；
  3. `intro.py`：12.5 秒自由時間前奏，之後接 84 BPM；fade 依時間線性。
- **修改輪（主要判定）：**
  - 漸快改在第 7～13 小節，全曲改為 17 小節；
  - 前段改成 5/8；
  - 前奏改成 10.0 秒。
- **兩組：**H 的作品資料夾裡有 `tclock.py`；P 什麼都沒有。其餘條件相同：同樣的 skill、
  用 `tactus init` 建立的作品，每組 3 個 fresh sonnet Agent。

## 結果（依音檔核對）

| | 第一輪 | 修改輪 | 最終 tokens（平均） | 三首程式碼行數 |
|---|---|---|---|---|
| H（有工具） | 3/3 全部逐樣本正確 | 3/3 | 85.8k | 146～188（平均約 164） |
| P（沒有工具） | 3/3 | 3/3 | 93.8k（1.09×） | 203～301（平均約 254） |

- H 組三人三首都用了 `tclock`。修改時只改 tempo 點、拍號數值或起始秒數，其他都自動跟著移動。
- P 組三人都自己推導出漸快的對數公式和它的反函數，用來算 sweep。修改時也只改少數常數，
  因為三人第一輪就把參數抽成了常數。P3 還自己寫了一個共用的 `_timeutil.py`。
- P2 在修改輪中途因為額度用完而中斷，恢復後完成。它的 token 數包含恢復的成本。
- 所有 Agent 都自己寫了獨立的驗證腳本，對照 render 出來的檔案檢查。

## 判讀

- **工具的好處只在程式碼量與 token：**程式碼少了約 35%，token 少了 9%，兩者都不影響正確性。
- **限制：**這三題都有精確的規格。真實作品的時間需求比較模糊，而且會在長時間修改中慢慢累積，
  這次沒有測到。唯一看到的「錯誤」仍然是 dogfood 3 的累加寫法，而且聽不出來。
- **重新考慮的條件：**實際作品出現時間計算錯誤（例如速度變化後有東西沒跟著移動），
  或 Agent 在修改時漏改了跟時間相關的地方。
